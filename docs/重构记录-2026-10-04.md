## 1. 把核验接回真机路径（P0-A）

**问题**：`SessionController` 给手机上的 `AgentLoop` 传的是 `CloudReviewer`（纯模型调用），而机械层 + 证据层只存在于 `RuleReviewer` → `CompletionAudit`。README 宣称的"三道铁门"、harness 的核验矩阵、X1/X4 对抗结论，测的都是另一条代码路径。

**改动**
- 新增 `MechanicalFirstReviewer`（`core/OutcomeCheck.kt`）：先跑 `CompletionAudit`，**只有返回 `Supported` 才**发起模型复核；本机拒绝是终局，模型调用无法把它翻回完成。
- `SessionController.buildLoop()` 改为 `MechanicalFirstReviewer(CloudReviewer(...))`。

**测试**：`MechanicalFirstReviewerTest` 两条——本机矛盾的声明（"已经帮您转账了"，无任何动作）**不触发模型调用**且结论非 Supported；无本机矛盾的声明正常转交模型。

**行为影响（必须知道）**：手机上现在会真正执行机械层与证据层，因此**此前被判为 `COMPLETED` 的部分任务会变成"待核对"**。这是设计意图（证据不足宁可承认无法确认），但会改变真机成功率数字，需要在评测时如实记录。

## 2. 堵掉"页面文字可以伪造办好了"（P0-B）

**问题**：`CloudReviewer.parse` 在 JSON 解析失败时对**整段模型输出**做正则找 `"verdict"`；而提示词又要求模型在 `citations` 里原样引用页面文字。一条含 `"verdict":"supported"` 的第三方页面就可能把"无法确认"翻成"办好了"。

**改动**
- 删除整段正则兜底。verdict 只来自两个**模型自己写的位置**：JSON 对象，或首行整行锚定的 `VERDICT: <word>`。
- 提示词要求第一行输出该标记（整行只有这一句），第二行起输出 JSON；这样即使 `citations` 里的引号写坏了 JSON，判断也不会丢。
- 锚定匹配 `^\s*VERDICT\s*[:：]\s*([a-z_]+)\s*$` 只作用于第一个非空行，页面引文不可能出现在那里。

## 3. 异常路径不再重放已执行的动作（P0-C / P1-3 / P1-8）

**问题**：`AgentLoop.execute` 只捕获 `CancellationException`。无障碍层抛任何其它异常时，异常逃逸 → 调用方当成"暂停" → **内存与落盘的 transcript 停在"assistant 有 tool_calls、没有 tool 结果"**，而 `loop()` 的 `pending` 分支会把整批动作**再执行一遍**。手机上的点击/输入不可撤销。项目自己的 mock provider 契约（`harness/mock_server.py:44-49`）明确禁止这种消息序列。

**改动**
- 每次调用包 `try/catch`：把风险段抽成 `runInvocation()`，catch 里为该调用写一条 `tool_error` 结果，**本批剩余调用写 `skipped_after_error` 并停止本批**，然后返回 `PAUSED`。结果未知的动作绝不重试（"点了但不知成没成"是显式状态）。
- 删除退化的 `pending` 字段、`awaitingApproval` 访问器与 `loop()` 的续跑分支（它在正常路径永远为空，只在损坏态为真）。
- `check{}` 断言换成防御分支：没有可挂载的 assistant 消息时返回 `PAUSED`，而不是在写完 assistant 消息之后崩溃。
- `AgentStep.Calls(emptyList())` 不再崩溃：计一次修复预算，超限则明确报告"模型连续给出空的操作请求"。
- `:app:compileDebugKotlin` 与全部测试验证通过。

**测试**：`AgentLoopFailurePathTest` 四条——抛异常不重放且跳过后继、抛异常后每个 `tool_call` 仍有唯一结果、空批次不崩溃、**整批重复调用计入修复预算而不是跑到步数上限**（修复前会跑满 40 步）。

## 4. 执行者自己输入的文字不再算证据（P0-D 来源部分）

**问题**：观察层把**输入框的当前文本**当作页面事实收进证据账本。于是 agent 往搜索框里敲 `4006`，下一轮就在页面上"读"到它，再用"取件码是4006"自证完成。

**改动**
- 新增 `writtenText` 账本：成功执行 `input_text` / `type_text` / `paste_text` 后记录其 `text`。
- 构建观察证据时，**同时从原始节点文本和渲染后的页面文本中剔除命中这些字符串的行**（长度 ≥ 2 才参与，避免单字符误伤）；`reset()` 清空。
- 方向刻意偏向"多删"：少一条事实只会让结果变"待核对"，多一条自供事实会让假"办好了"成为可能。

**测试**：`AgentSelfEvidenceTest` 两条对称用例，同一个页面、同一个结论，只有数字的来源不同——自己敲进去的 → `PAUSED/OUTCOME_UNVERIFIED`；页面本来就显示的 → `COMPLETED`。**已验证该回归测试在关掉修复后会失败**（不是空转的测试）。

**仍未修**：声明里没有可解析事实时的"默认放行"（`OutcomeCheck.kt:500`、`EvidenceCheck.kt:69` 的早退 `Supported`）。收紧它有真实的保守代价，需要消融数据来定，留待阶段 3。

## 5. 配对身份不再由加入者自选（P0-F）

**问题**：6 位配对码（≈30 bit）、1 小时 TTL、**无失败计数**；`/join` 的身份由加入者在表单里选，非法值回落 `family`。拿到（或爆破出）码的人可选"家人"读全部上下文，并用 `/family/message` 让老人手机**大声朗读"家人留言"**——正是电诈需要的通道。

**改动**
- **身份跟随邀请码**：新增 `devices.pair_code_role`（含旧库迁移）；`/join` 完全忽略表单的 role。
- 新增 `POST /api/device/invite`（需设备令牌）：按角色轮换邀请码，旧码立即失效。
- 手机端设置页把"配对码"改为"邀请码"，并新增**邀请家人 / 邀请社区 / 邀请邻居**三个按钮（此前社区/邻居只能靠加入页自选，这个入口是必须补的）。
- 配对码 6 位 → **8 位**（≈40 bit），加入页 `maxlength` 同步。
- **按来源 IP 限速**：10 分钟窗口内 5 次失败后返回 429；限速期间即使给出正确码也返回 429（猜测者无法从差异中获得信息）。计数器为进程内状态，与单进程部署匹配，测试装置里逐用例清空。
- 配对码不再写入 logcat（`ServerClient`）。

**测试**：新增 3 条 + 改造既有用例——加盟者带 `role=family` 表单也只能成为邀请码指定的邻居；连续错误码被限速且正确码同样被拒；`invite` 需要设备令牌且拒绝未知角色。服务端 **34 项全绿**。

**仍未做**：配对码用后不失效（多次加入同一角色）；配对码比较未用 `compare_digest`（已有限速，索引时序侧信道不是边际风险）。

## 9. 证据来源进入数据模型，审计真的用它（provenance）

**改动**
- 新增 `EvidenceSource { PAGE, TOOL, SELF_TYPED }` 与 `Observation.source`；`origin` 在未显式指定时按"有 `tool` 就是 TOOL，否则 PAGE"推导，因此既有构造点（含 harness 的核验矩阵）无需改动。
- 审计改为**按来源过滤**，而不是按内容过滤：只有 `aboutTheWorld` 的来源（PAGE / TOOL）能为一件事背书；敏感页仍然整体不贡献。
- 执行者自己输入的文字**不再被悄悄丢弃**，而是记成一条 `SELF_TYPED` 观察。这样审计能区分"我从没看见"和"这是你自己敲进去的"，并给出后者——对老人和家人才是能听懂的解释。
  实测提示语：*"结论里的「4006」是执行助手自己输入到手机里的文字，页面上并没有看到这个事实"*。
- `Observation.app` 从死字段变成判据：**不同应用显示同一个字段的不同值时，不再让"最新的那个"替另一个背书**（此前会静默取最新值判为 Supported）。两个应用显示一致时仍然放行；`app` 为空的历史调用按"单一未知来源"处理，行为与之前完全一致。

**测试**：`EvidenceCheckTest` 新增 4 条——自己输入的文字不能背书且提示语含"自己输入"、本地工具（时钟）的事实仍然有效、两个应用对同一字段不一致 → 待核对、两个应用一致 → 支持。`AgentSelfEvidenceTest` 的端到端用例补强为断言提示语本身，确保走的是 provenance 路径而不是碰巧返回了 Unverified。

## 12. 所有工具执行走同一条闸门（P0-E）

**问题**：`captureWhenBlind()` 在盲页/图形页上自己调 `tools.execute(...)`，完全绕过审批——而 `screenshot` 在工具目录里明确声明了 `needsApproval = true`，审批台词也早就写好了。更糟的是 app 层的 `needed()` 只对 `tap_xy` 返回 true，所以这个"同意"在手机上从来没有真正发生过，而截图是要**离开手机**发到云端视觉模型的。

**改动**
- 抽出 `dispatch()` 作为**唯一**的执行入口，模型发起的调用与循环自己发起的调用都走它。加一个新的内部调用者不再可能绕过闸门。
- `refuse()` 是闸门链，顺序固定且单调：参数校验 → 本人操作词表 → 敏感页 → 同意。谁都不能放行被后一道拒绝的东西。
- 批量预审批改为**只对真正会执行的调用提问**（`staticRefusal` 提取出来复用）。此前是"先问后校验"，所以一个 `x="abc"` 的调用也会先打扰老人——这是新测试抓出来的。
- app 层：`screenshot` 现在会**按任务问一次**"要把这一屏发给视觉模型吗"，同意与拒绝都记住（拒绝不会变成每页都问）。演示模式（`autoConfirm`）仍然直接放行。
- 盲页截图补上 revision 去重：`graphicalShotRevision` 改名为 `autoShotRevision` 并在两个分支都生效。此前只有图形页有去重，**盲页的控件树永远不变，于是每一步都重新截图并重新上传同一屏**。

**测试**：新增 `ToolGateTest` 6 条——自动截图先征求同意且拒绝后不产生截图、盲页只截一次（`maxSteps=5` 下恰好 1 次）、非法参数不打扰老人且回传 `invalid_x`、超出范围的比值被拒而不是被 clamp、**屏幕尺寸未知时不会变成屏幕中心的一次真实点按**（`x=-1` 由服务端以 `out_of_bounds` 拒绝）、`swipe` 时长越界被拒。

## 13. 参数校验补齐类型与区间（P1-7）

**问题**：`validate()` 只查"存在性"。`x="abc"` 能通过，然后在 `resolveCoordinates` 里被 `toFloatOrNull() ?: 0.5f` 变成 **0.5**，再乘上兜底的 1080×2400 —— 一次静默的、屏幕正中心的真实点按。同理未知屏幕尺寸也会被兜底成 1080×2400。

**改动**
- 按目录声明的 `param.type` 校验 `number`/`integer` 是否可解析，不可解析就返回 `invalid_<参数名>`。
- `tap_xy` 的 x/y 是屏幕比例，超出 `0..1` 一律拒绝（不再 `coerceIn` 成边界值）。
- `durationMs` 按其工具声明的区间校验（`wait` 100..5000，其余 100..1500）。
- `resolveCoordinates` 去掉所有"魔法兜底"：比例非法或屏幕尺寸未知时返回 `x=-1`，由服务端的 `out_of_bounds` 拒绝，而不是替模型随便挑一个位置。

## 14. 上下文预算与折叠式压缩（P1-4）

**问题**：每一步追加一整页渲染（约 140 个控件），**从来没有删除过任何东西**。`maxSteps = 40` 是唯一的上界；没有任何 token 预算、历史压缩或 `prompt_too_long` 处理。长任务必然把请求撑爆，成本与延迟还随步数平方增长。

**改动**
- 新增 `compactIfNeeded()`，在每步规划前调用：估算超出预算的 80% 时折叠最老的页面渲染，保留最新 16% 的内容。阈值与比例沿用 DSH 的形状（0.8 / 0.16）。
- **只折叠页面渲染**（`当前页面：` 开头），从不折叠人自己的诉求、也从不折叠动作记录。这一条是刻意的：完成核验的动作账本是从 transcript 反推的，而观察事实存在独立的证据账本里——所以折叠对审计**零损失**。
- 图片只保留最新的：折叠时把旧消息上的图去掉。估算里给每张图记 1200 token。
- token 估算是粗糙的启发式（CJK 按 1、其余按 1/4），与 DSH 自己也有启发式兜底的做法一致；它只需要好到能发现"这个请求快撑爆了"。
- `contextBudgetTokens` 是构造参数，设 0 可完全关闭折叠（评测做消融时用得上）。

**代价（如实）**：折叠会重写历史消息，因此从被折叠处起前缀缓存失效。这与"只追加"的缓存设计是一对取舍——只有在请求快要超出预算时才会发生，那时不折叠就没有请求可发。

**测试**：新增 `ContextBudgetTest` 5 条——超预算后确实折叠、人自己的话永不被折叠、**动作记录在折叠后仍然完整**（4 组 assistant/tool 配对还在）、最新一页仍然可见、预算为 0 时不折叠。已**验证关掉折叠后其中 3 条会失败**，不是空转。

## 17. 流式请求与真正可用的取消

**问题**：`HttpURLConnection` 的阻塞读**不会响应协程取消**。实测：让 mock 提供方接受请求后静默 60 秒，按下"停下"后仍然等了 **45050ms**（45 秒读超时生效），而不是被取消。对这个产品，"停下来"按下去不生效是安全问题，不只是体验问题。另外请求全量缓冲，老人要面对 5–45 秒的绝对静默。

**改动**
- 新增 `core/OpenAiStream.kt`：OpenAI 兼容流式响应的**纯逻辑**累积器，无任何传输依赖，因此累积规则可以直接单测。它处理的是流式真正会出错的地方——工具调用按 `index` 分片到达、名字可能只出现一次、参数分几十帧下发、部分提供方只在第一帧带 `index`、`usage` 只在最后一帧、`finish_reason` 可能单独一帧。同时把 `parseToolArguments` 提到 core，去掉 app 层的重复实现。
- `CloudPlanner` 改为发 `stream: true` + `stream_options.include_usage`（否则用量帧不会下发，评测赖以成立的缓存命中率会静默消失），逐帧解析，并在**每一帧之间检查取消**。
- **取消机制**：`withCancellableConnection` 起一个伴生协程守在取消信号上（`awaitCancellation()`），取消时立刻 `disconnect()` 关闭 socket。这里踩了一个真实的坑并写进了注释：直觉写法 `job.invokeOnCompletion { if (it is CancellationException) disconnect() }` **看起来对、实际什么都不做**——该回调在 job *完成*时触发，而卡在阻塞读里的 job 永远不会完成。这正是"取消看似生效、其实没生效"的成因。
- 取消导致的 `IOException` 会被识别回取消（`ensureActive()`），不会被报成"网络没有连上"。
- **非流式回退**保留：按 `Content-Type` 判断，若响应体本身以 `data:` 开头也按 SSE 解析（有些代理会把流式响应重新缓冲并标成 `application/json`）。若提供方不认 `stream` 而回 400，自动不带流式重试一次。
- 新增 `AgentHook.onThinking()`（每次请求调用一次，重试不重复），app 端显示"正在想办法…"，避免模型思考期间屏幕完全静止。`onDelta` 在 app 端接了一个每秒最多一行的诊断日志——流式在真机上本来是隐形的，没有它就无法确认流是否真的在到达。

**测试**
- `OpenAiStreamTest` 10 条：内容分片拼接、工具调用跨多帧组装、**两个交错的调用各自保留参数**、缺 `index` 的后续帧归到唯一打开的调用、usage/缓存命中、截断与空响应、坏帧不丢整段回答、无名字的调用被丢弃、参数非法 JSON 降级为空。
- **harness 新增场景 32（在途请求取消）**，并给 mock 加了"接受请求后静默"的模式。这条测试是**先失败后修好**的：第一版实现耗时 45050ms（读超时），改用伴生协程后 1502ms（等于测试自身的等待时间，即取消几乎瞬时）。
- mock 现在按真实提供方的方式分片下发（内容每 2 字、参数每 3 字）。**所以 harness 全部 32 组场景都在跑流式路径**——分片重组错了，`tap_text`/`scroll` 的参数就会损坏，场景立刻失败。已用 `/tmp/mockai/payload.json` 确认 harness 的请求确实带 `stream: true` 与 `stream_options`。其中 `claim` 模式故意返回非流式响应，让缓冲回退路径继续留在回归里（否则开启流式会静默退掉这条覆盖）。

**未做**：`onDelta` 没有接到语音或悬浮窗实时文案上。流式的答案文本目前只在结束时使用；把它逐字念出来对老人没有帮助（模型的中途输出不是给老人看的话），所以只保留了诊断用途。若要"边想边说"，需要在 core 里区分 reasoning 与最终答复，那是另一件事。
