## 一、逐处改动（文件 / 函数级）

### ① `requires` 没有接线到运行时

**问题回顾**：Tier1 影子率 πm 用 `apps ∧ requires` 算（`SkillShadow.replay` / `tasks/skill_replay.py`），而运行时决定“端不端给模型”的 `SkillCatalog.hintFor/selectFor` 只看 `apps`(+`goal_family`)。门禁数字与线上行为不一致。

| 文件 | 函数 | 改动 |
|---|---|---|
| `core/src/main/kotlin/com/yinling/core/SkillGate.kt` | `SkillShadow.OBSERVATION_TAIL_MARKERS`（新增） | 与 Python `OBSERVATION_TAIL_MARKERS` 逐字一致的 4 个“非页面装饰”标记：`" \| 已安装应用（"`、`"已安装应用（"`、`"提示："`、`"（对老人说的每句话"`。 |
| 同上 | `SkillShadow.observationFor(rendered): String`（新增，纯函数） | 从 `当前页面：` 起、截到第一个装饰标记为止；**取不到 `当前页面：` ⇒ 返回空串**（不静默退回 apps 单条件）。与 Python `observation_from_payload` 同语义。 |
| 同上 | `SkillSelect.surfaced(skill, app, goalFamily, observation): Boolean`（新增） | 运行时的唯一规则：`matches(app, goal_family) ∧ requiresSatisfied(requires, observation)`。`observation` 是**必填**参数，刻意不给默认值，防止将来又悄悄退回 apps 单条件。 |

## 四、① 的观察文本剥离口径：Kotlin / Python 是否共用同一语义？怎么防漂移？

**结论：语义共用，实现仍是两份源码（跨语言无法共享二进制），用“同一张 golden 表 + 源码级标记比对”双向钉死。**

1. **单一事实来源的 golden 表**：`core/src/test/resources/skill_observation_golden.tsv`
   - 每行 `<rendered>|||<expected observation>`，`\n` 转义，`#` 注释。含 9 条用例：完整渲染（页面+安装列表+提示+中文尾）、提示在安装列表之前、提示自带前导换行、只有中文尾、` | 已安装应用（` 变体、无尾部、无 `当前页面：`、空串、敏感页早退。
   - **Kotlin** `SkillObservationGoldenTest` 从 classpath 读它，断言 `SkillShadow.observationFor`。
   - **Python** `server/tests/test_skill_observation_golden.py` 从仓库同一路径读它，断言 `tasks/skill_replay.py:observation_from_payload`。
   - 任何一侧改了切割规则，它自己那套先红。
2. **标记列表逐字比对**：Python 测试用正则从 `SkillGate.kt` 里抠出 `OBSERVATION_TAIL_MARKERS` 的字符串列表，断言 `== list(skill_replay.OBSERVATION_TAIL_MARKERS)`。所以即使新增了一个当前 golden 没覆盖到的标记，也会红（实验 1c 实测）。
3. **语义细节两侧一致**：都取 `当前页面：` 起、到最早标记止、`trim()`；都无 `当前页面：` ⇒ 空串；`requiresSatisfied` 两侧都是 `observation.contains(entry, ignoreCase=true)` 的 `all`。
4. **注意边界（未做）**：这只是**测试级**的防漂移，不是编译期共享；若有人同时改两侧且同步更新 golden，测试不会拦（这是合理的，因为那是同一语义变更）。另外 Python 侧的 `observation_from_payload` 还被真实日志适配器调用，Kotlin 侧的 `observationFor` 还被运行时 `SessionController` 调用。

## 五、③ 改名是否影响已持久化数据？（查清楚了）

**不影响。** 逐条实测/查证：

1. **唯一被序列化的地方**是 `AgentLoop.renderResult`：
   `append('\n').append("本地核验：").append(result.effect.name)` → 写进的是**枚举常量名**（`APPLIED/…/NO_EFFECT`），不是类型名。读回时 `parseEffectMarker` 用 `ActionEffect.entries.firstOrNull { it.name == name }` 比对常量名。这次只改了**类型名**（`Effect`→`ActionEffect`、业务 `Effect`→`WorldEffect`），**常量名一个都没动**，所以旧 transcript 里的 `本地核验：NO_EFFECT` 照旧解析。
2. 全量测试里已有真实回执：`harness/Harness.kt:1961` 断言 `loop.conversation.any { it.content.contains("本地核验：NO_EFFECT") }`，改名后 harness 仍 208/208 全绿。
3. `app/.../SessionStore.kt` 持久化的是消息 `content` 字符串，以及 `outcome{success, screen_changed}` 两个字段；**没有** `effect` / `Effect` 字段（已在 `SessionStore.kt` 全文件 grep 无命中）。
4. `server/`（Python/SQLite）与 `tasks/` 里没有任何地方写 `Effect` 类型名或枚举名（grep 无命中）。
5. 结论：无需读取处兼容；已有 session JSON / SQLite / archived transcript 不受影响。

**未处理（如实标注）**：仓库文档里仍有过时描述——`交付-机制ABC-实现与验证.md` 第 21/30/39 行仍写 `effect: Effect`、内嵌 `ToolResult.Effect` 与 `private typealias ActionEffect`；`docs/aic-2026/作品方案-定稿.md` 有若干 `Effect` 叙述。按“其余文件尽量别动”的纪律**没有改文档**，仅在此标注为待更新。

## 六、不确定处与没做的部分

1. **`SkillCatalog` 的接线没有 JVM 单测**。app 模块没有 `src/test`（只有 `src/main`），所以 `hintFor`/`selectFor` 的实际调用只能靠 `:app:compileDebugKotlin` 编译验证；其判定规则被抽到 core 的 `SkillSelect.surfaced` 并用 `SkillSurfaceRequiresTest` 钉住，但“`SessionController` 真的把 `observationFor(page)` 传进去了”这一步**没有自动化测试**，只有代码审查 + 编译通过。
2. **`selectFor` 没有生产调用点**（全仓 grep 确认）。签名与语义已改并测试，但线上行为不经过它。
3. **CloudPlanner 的三处 `REVIEW_FAILED` 没有自动化测试**。`CloudReviewer` 在 harness 里没有被构造（harness 只用 `CloudPlanner` 当 planner），core 也测不到；只做了编译验证。这里有一个**如实说明的行为变化**：模型自己返回 `"unverified"` 的自由文本 reason（`parse` 的 `else` 分支）不再被关键词反推，保留默认 `WORLD_UNOBSERVED`，因此过去那种“reason 里带『不一致』会被判成 CONTRADICTED、不给重试”的情况，现在会走一次有界重试。这是“不按文案分流”的必然结果；如果产品希望模型侧也显式给 gap，需要在 reviewer 协议里加字段（本轮没做）。
4. **`EvidenceGap` 的分类是人工对照文案判断的**，没有形式化规范。可能存疑的两处：a) `"结论中的汇总数量缺少同单位的总数依据"` 我判为 `WORLD_UNOBSERVED`（可重试去看），不是 `CONTRADICTED`；b) `"结论中「X」没有绑定到页面上的「field」"` 判为 `WORLD_UNOBSERVED`。两者都符合任务给出的对照口径，但若产品想要不同分流，改 `EvidenceCheck` 一处即可，测试会跟着红。
5. **没有跑真机 / 没有跑 `:app:test` 或 instrumented 测试**；没有运行 `tasks/skill_replay.py shadow` 的真实日志回放（`tasks/runs/` 在 `.gitignore` 里，本轮未见存档日志）。
6. 本轮**没有**改动 `docs/`（除上面指出的过时描述），**没有**执行 `git commit/checkout/stash`。工作区里另有若干**非本轮改动**的已修改/未跟踪文件（如 `MainActivity.kt`、`SkillStore.kt`、`RealDeviceRegressionTest.kt` 等），是进入本轮前就存在的状态，我未触碰。
