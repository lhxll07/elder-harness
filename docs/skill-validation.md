# 经验技巧：候选、试用、验证、采用

目标是复用已验证的做法，不是让模型自行宣告“学会了”。没有另加向量库、训练服务或自动发布器。

## 使用闭环

1. 老人确认任务确实完成后，模型可以生成候选。文件始终重置为 `pending`，正文声称 `pass` 无效。
2. 开发版开启高级调试，在技巧页选“下个任务试用”。只影响下一个新任务及其续办，自动确认强制关闭，首页标注实验；只能使用可撤销任务、虚拟数据，不用于真实付款/发送。
3. 在不同于提炼来源和失败基线的运行上独立核实结果：至少两次目标成功，覆盖目标任务和原本通过的旧任务。保留失败运行，不能只挑成功的记录。
4. 依据归档编制 JSON 验证报告，在技巧页“导入独立验证报告”。应用重新核对契约、准入与影子回放，不接受报告自带的 `pass`。
5. 报告通过后家人才能点“采用”；可退休或回退到仍有有效验证报告的已采用版本。重启/恢复历史任务不自动恢复候选试用。

正式版没有候选试用入口。试用也不能越过付款、发送、身份验证、敏感页或系统设置范围约束。候选只提供建议，不获得执行权限。

## 报告结构

| 字段 | 内容与约束 |
|---|---|
| `skill_id`, `version` | 本机保存的候选标识和版本；不是提炼前的草稿版本 |
| `skill_hash` | 候选 Markdown 中的 `content_hash`，兼容既有版本链 |
| `contract_hash` | Markdown 中的 SHA-256 `contract_hash`；覆盖正文、适用应用、任务族、前提、校验器、禁用项、描述与提示等 |
| `target_tasks`, `regression_tasks` | 非空、去重且互不相交的任务编号数组 |
| `runs` | 独立运行数组，格式见下文；不能包含提炼 `evidence_run` 和失败 `baseline_run` |
| `points` | 决策点数组，含 `run_id/task_id/app/goal_family/step/observation`；每个运行须留点位，运行与任务对应 |
| `baseline` | 同任务、同重复次数的对照总量，含正整数 `steps/tokens`，用于防止开销退化超过 30% |

每条 `runs` 必须显式提供：

- `run_id/task_id/skill_hash`，运行编号不可重复。
- `auto_confirm: false`；`real_outcome: "done"` 或 `"not_done"`，未知不得替代成功。
- `false_done` 布尔值；`sensitive_actions` 为独立审查发现的**实际越界执行数**，不是被成功阻止的动作数。
- `steps/tokens` 正整数；`baseline_passed` 表示该旧任务是否在对照中通过。

目标成功运行必须包含满足该技巧应用、任务族和前提的点位；所有回归任务须有原本通过且仍然完成的记录。应用自行计算影子率，拒绝不安全动作、谎报、缺少回归、开销退化及无有效观察等情况。

开发版可用 `adb exec-out run-as com.yinling.hotline cat files/skills/versions/<id>/v<version>.md` 导出候选。`tasks/skill_replay.py` 可分析归档决策点；现有 `tier2` 输出仅为离线预览，不能直接当作本机验证报告。新运行的 `.manifest.json` 记录来源和实际加载的技巧，老记录缺少这些信息时不得补造。

## 信任与能力边界

契约哈希只防止“拿另一版本或另一适用条件的报告来启用”，不是数字签名，也不能证明人工标注是真的。报告由受信任操作者编制；当前没有第三方数据认证、统计显著性证明或已测得的技能泛化收益。界面里声明的校验器名称属于契约信息，不代表每个名称都已经接通了独立的业务回执。

采用与加载检查有效证据和实际页面前提；被采用并不保证永远有效。应用更新、页面变化或出现错误后应退休并重新留档，而不是修改旧报告为“继续通过”。
