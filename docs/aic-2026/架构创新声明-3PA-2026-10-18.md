# 3PA · 三平面可信执行架构

> **定位**：这是本作品的架构创新声明，不是功能清单。它把已有的四条机制重新组织成三个平面与四条跨平面不变量，并把每一条都锚到代码、测试与数字上。
> **用途**：① 替换答辩里“四项机制”的叙事；② 作为方案书新增一节（建议 2 页 + 1 图）；③ 与形式化三节（A/B/C/D）互相引用。
> **一句话**：**手机智能体的可信，不在模型里，而在“动作—页面版本—证据来源”的三重绑定里。**

---

## 1. 旧叙事的问题

现在讲的是“四项机制”：可逆性分级、完成核验、双通道观察、按需经验。这是**清单**，不是**架构**：

- 四条之间没有共同的不变量，评委无法判断“少一条会怎样”；
- 其中两条（双通道、按需经验）与“可信”是弱关联，讲多了反而稀释主张；
- 真正撑住“可信”的第三条腿——**页面版本绑定**——在报告里只以 `stale_screen` 的形式出现，没有被当成架构的一部分。

把代码读完可以看到：四条机制其实分布在**三个平面**上，而且共享同一组不变量。把这三个平面讲清楚，比列四条机制更有辨识度，也更能解释“为什么这套东西难以复制”。

## 2. 三个平面

```
                    ┌─────────────────────────────────────────┐
                    │  3PA · 三平面可信执行                    │
                    └─────────────────────────────────────────┘
        ┌───────────────────┬───────────────────┬───────────────────┐
        │ P1 绑定面          │ P2 授权面          │ P3 证据面          │
        │ Binding            │ Authorization      │ Evidence           │
        ├───────────────────┼───────────────────┼───────────────────┤
        │ 动作绑定到被观察的  │ 类型化工具语义 +    │ 来源分型账本 +      │
        │ 页面版本；跨版本只  │ 单调闸门 + 派发前   │ 跨应用不互证 +      │
        │ 允许唯一身份重绑；  │ 二次观察 + 一次性   │ 否定感知引用 +      │
        │ 坐标绝不跨版本      │ 授权               │ 完成声明携带证书    │
        └───────────────────┴───────────────────┴───────────────────┘
                    │                   │                   │
                    └───────────┬───────┴───────────┬───────┘
                                ▼                   ▼
                        I1 无孤儿动作        I2 无孤儿声明
                        I3 授权不可复用      I4 无未分类动作
```

**与“四层架构”的关系**：四层（交互 / 核心 / Android / 云端）是**部署视图**；三平面是**信任视图**。同一套代码，两种切法，不矛盾。

### P1 绑定面（Binding）

**主张**：一个动作只对**它被决定时看到的那一版页面**有效。

- 坐标动作（`tap_xy` / `type_text` / `paste_text` / `swipe`）**只在同一 revision 内有效**，跨版本一律拒绝（`stale_screen`）；
- 控件动作（`click` / `tap_text` / `input_text` / `scroll`）跨版本时，只允许**唯一身份重绑**：先按几何，再按“文字 + role + 父子结构”的几何无关身份；只有唯一匹配且该控件自己接受该动作时才重绑；
- 派发前**重新观察**一次页面，用新版本重绑——不是在计划时判断、执行时照旧。

代码：`ScreenActionGuard.rebind`（`core/.../ScreenActionGuard.kt:9`）、`AgentLoop.dispatch` 的 `dispatchScreen = tools.observe()`（`core/.../AgentLoop.kt:1350`）。

**为什么这是架构而不是补丁**：它把“页面会变”从异常变成了**一等公民**。没有这一层，闸门与核验都建立在一个已经不存在的页面上。

### P2 授权面（Authorization）

**主张**：放行权在本地，且闸门是**单调**的——后一层不能放行前一层拒绝的动作。

四个代码事实：

1. **类型化工具语义**：22 个工具的 11 个布尔属性（是否需要审批、是否触屏、是否算进展、是否改变状态、是控件还是坐标……）来自**一张枚举表**，不再散落在多个字符串集合里；`PhoneToolRegistryTest` 保证枚举与模型可见目录一致。新增工具若忘了分类，测试直接失败——**不存在“未分类的动作”**。
2. **单调闸门**：参数校验 → 文本词表 → 敏感页 → 本人同意，逐层短路；注释原话是“none can grant what a later one refuses”。
3. **派发前二次检查**：`dispatch` 先 `refuse`（含审批），再重新观察、重绑、**再跑一次** `ManualActionPolicy.checkScreen`——防的是“计划时安全、派发时页面已变”的 TOCTOU。
4. **一次性授权**：确认走单个 `CompletableDeferred`，`finally` 里清空；拒绝会被记住（截图/盲点不再重复问）；`autoConfirm` 只在 `BuildConfig.DEBUG` 下可用，且仍然校验、仍然绑定版本、仍然记日志。

代码：`core/.../PhoneTool.kt:3`（单一声明）、`core/.../AgentLoop.kt:1332`（唯一入口）、`core/.../AgentLoop.kt:1375`（闸门顺序）、`app/.../SessionController.kt:825`（确认）、`:873`（新应用）。

### P3 证据面（Evidence）

**主张**：完成声明不是一句话，而是一张**可检查的证书**；证书只能由“关于世界”的事实构成。

五个代码事实：

1. **来源分型**：`EvidenceSource.PAGE / TOOL` 的 `aboutTheWorld = true`，`SELF_TYPED` 为 `false`——执行者自己敲进输入框的字，会被页面“回声”出来，但它不是世界的事实。
2. **账本有界**：最多 60 条观察；没进账本的事实不能为完成背书。
3. **跨应用不互证**：两个应用对同一字段给出不同值时，判“待核对”，不取“最新的那个”。
4. **否定感知**：页面写“未签收”，不能为“已签收”背书；数字引用必须是页面自己的数字，不能是日期或编码里的一段。
5. **最新优先 + 同类回退**：同一类事实只看最新一次观察；最新一次没有记录该类事实时，回退到“最近一次记录过该类事实”的观察——避免“再看一眼反而毁掉证据”。

代码：`core/.../EvidenceCheck.kt:20`（来源）、`:57`（账本）、`:97`（校验）、`:141`（跨应用）、`:277`（最新优先）、`:300`（否定感知）；`core/.../OutcomeCheck.kt:675`（两级串联）。

## 3. 四条跨平面不变量

| 编号 | 不变量 | 代码锚点 | 测试锚点 | 现有数字 |
|---|---|---|---|---|
| **I1** | 无孤儿动作：任何副作用都有当前版本绑定 + 闸门放行 | `AgentLoop.dispatch`、`ScreenActionGuard` | `AgentLoopDispatchTest`、`ScreenActionGuardTest`（13） | S4/S1 后两轮零盲坐标；`stale_screen` 独立计数 |
| **I2** | 无孤儿声明：任何“完成”都有世界来源、晚于动作的证书 | `EvidenceCheck`、`MechanicalFirstReviewer` | `AgentSelfEvidenceTest`、`EvidenceCheckTest`（23） | 0/22 → 12/22 → 22/22；1/10 |
| **I3** | 授权不可复用：一次性、参数绑定、不跨动作/版本转移 | `SessionController.confirm`、`AgentLoop` 审批 | `AgentLoopReliabilityTest`（19）、`ToolGateTest`（6） | 审批前执行数 = 0；拒绝不重复问 |
| **I4** | 无未分类动作：工具语义来自类型化注册表，目录与注册表测试一致 | `PhoneTool` 枚举 | `PhoneToolRegistryTest` | 22 个工具、11 个属性、单一来源 |

**这四条不变量就是“架构”**：评委不必记住四个机制名，只要问“这四条成立不成立”，答案都在代码与测试里。

## 4. 与前沿工作的差异

| 工作 | 它解决什么 | 它没有解决什么 | 3PA 的差异 |
|---|---|---|---|
| CaMeL（arXiv:2503.18813） | 控制流与数据流分离、能力化执行 | 页面版本绑定、完成证书、来源分型 | 信任单元从“能力”变成“动作—版本—证据”三元组 |
| AgentDojo（arXiv:2406.13352） | 注入攻击的**基准** | 运行时机制 | 我们给机制，不给基准 |
| Mobile-Agent / AppAgent / AutoDroid | 把手机操作**做对** | 安全与可信是可选优化 | 能力之外加三平面约束 |
| ElderBench | 适老**评测**，249 任务 / 20 应用 | 不提出方法 | 我们给运行时可强制的结构 |
| 通用 guardrail | 在模型/工具边界检查 | 不与页面版本、完成证书联动 | 单点检查 vs 跨平面不变量 |

**一句话差异**：别人把可信做成**一次检查**，我们把它做成**三个平面之间的绑定关系**。检查可以被绕过，绑定关系不行——因为你绕不过“动作属于哪一版页面、证据来自哪里”这两个问题。

### 一个必须同时讲清的口径

“29/31 落在设计内收尾”**不等于 29 条成功**：其中 6 条完成、7 条主动提问、3 条到达本人边界、13 条暂停（含等待页面恢复）。**完成的 6 条是“能完成”的子集，不是成功率。** 这句话要跟数字一起出现，否则就是把“设计内”偷换成“成功”。

## 6. 诚实边界（必须写进正文）

1. **3PA 是运行时结构，不是语义正确性证明**。闸门依赖 H1（分类完备），5/6 边界探针就是 H1 失效；架构保证的是“失效有界、可审计、可交还”，不是“不会失效”。
2. **I2 只覆盖“声明与本轮记录一致”**，挡不住“确实动了手却没做成”——那要前后截图对比。
3. **I3 的一次性授权是工程不变量**，不是密码学保证；它防的是重复与串用，不防恶意进程。
4. **83—84 是写作与代码的上限**，不是评委的承诺；如果评委不买“架构”这个叙事，仍会按 74—78 打。
