# 冲国奖：必须补足清单

> 依据：AI+软件创新评分规则（创新性 20 / 技术实现 20 / 功能完整性 20 / 方案完整性 20 / 应用价值 15 / 总结与展望 5）
> 现状核查日期 2026-10-03，基于 `作品方案-定稿.md`（63,061 字 / 46 表 / 87 文献）与代码库实际状态。
> 分三级：**P0 不补就没法参赛或直接丢分**、**P1 决定能否进国奖**、**P2 补强可信度**。

---

## 〇、总判断

**技术侧已经具备国奖竞争力**：137 项回归断言、31 项 pytest、五组对抗实验（含修复前后对照）、真机验证、87 条文献且 56% 为 2025—2026 年、四个诚实披露的边界。

**但现在的短板不在技术，在三处**：

1. **形式性硬要求没补齐**（4 项【待补】、无演示视频、无网盘链接）——这部分**成本极低但直接扣"方案完整性"20 分**；
2. **没有真人用户验证**——适老产品却**零老年用户数据**，这是评委必问、且"应用价值 15 分"的主要依据；
3. **核心创新点只做了一半**——"证据层核验"是我们区别于 ElderBench 的关键，目前只有机械层。

## 二、P1：决定能否进国奖的三件事

### P1-A　老年用户试用（**最高优先级，且目前完全为零**）

**现状**：报告 1063 行自陈"目前没有正式的老年用户试用数据"；八（二）还写着"尚无正式的老年用户试用数据与商业合作意向"。

**为什么这是最大缺口**：
- 这是一个**适老产品**，却没有任何一位老年人用过——评委的典型提问是"你怎么知道老人用得来？"；
- 评分表中"**应用价值 15 分**"的主要依据就是真实需求验证；
- "**功能完整性 20 分**"也看"是否真的可用"，而不只是"代码写完了"；
- 我们手里**已经有**可安装的 APK，做这件事的边际成本比任何新功能都低。

**最小可行方案**（不需要伦理审查规模，但要规范）：
1. **5—8 位老年人**（可含队员祖辈），年龄、手机使用年限、是否用智能手机 三项基本背景；
2. **知情同意**：说明会被观察、可随时停止、不涉及真实资金（用测试账号或只走到提交前）；
3. **3 个任务**：发起一次查询（如查快递）、一次需要"交还本人"的任务（如走到支付页）、一次"办不成找家人"；
4. **记录四项指标**（与报告中的研发目标对齐）：
   - 能否**独立发起**（不看说明书）；
   - 能否**理解当前状态**（"它现在在干嘛"）；
   - 能否**中止**；
   - 遇到卡点时能否**找到真人帮助**；
5. **报告写法**：明确写样本量小、非对照实验、只是可用性观察，不给统计推断。

> **诚实提示**：不要把它包装成"用户测试通过"。写清"5 位老人、单机型、观察性"，比编造一个有统计意义的结果安全得多，也符合本报告一贯口径。

### P1-B　把"证据层核验"做完（核心创新点只做了一半）

**现状**：
- 六（八）第 2 条、八（五）第 1 条都写着"完成核验只到机械层，无法判断屏幕上是否真的出现了成果"；
- 三（三）7（5）里我们靠"**它没有安全与可信维度**"区别于 ElderBench——而**我们自己的可信维度也只做了一半**。

**为什么值得投**：
- 它是"创新性 20 分"里最实的一块（机械层核验已有真实谎报案例佐证，证据层是自然延伸）；
- 它是"功能完整性"里唯一的**未完成核心功能**；
- 做完之后，"证据层核验 + 机械层核验"才构成完整闭环，与报告标题里的"可信"二字匹配。

**最小可行方案**：任务开始时留存关键页面的控件状态指纹 → 收尾时重新采集 → 比对"声称改变的东西是否真的变了"；证据不足时输出"尚不能确认"（`OutcomeCheck` 已有该分支，只需接上外部证据源）。

### P1-C　与基线的对比实验（把"自证"变成"对照"）

**现状**：报告自己承认"**对比实验待开展**"。目前的强数据（美团打扰 0 次、漏拦情况）都是**单组自证**，没有对照组。

**为什么重要**：评分表"技术实现 20 分"看的是"能不能证明有效"。**有对照组的数据才叫实验，没有的叫演示。**

**最小可行方案**（用现成的回归套件，成本最低）：
- **完成核验**：无核验 / 机械核验 两组，比**虚假完成率**；
- **执行约束**：逐步确认 / 固定词表 / 分级执行 三组，比**漏拦率、误拦率、每任务确认次数**；
- 这三组 harness 里已有大部分场景，**主要是补编排与统计输出**。

| 评分项 | 分值 | 现状强度 | 主要缺口 |

## 五、建议执行顺序

```
第 1 周   P0 组 7 项（团队分工 / 模型口径 / PDF / 网盘 / 代码包整理）
         └ 同时启动：老年用户试用的招募与脚本设计   ← 周期最长，必须最早启动
第 2 周   录制演示视频（依赖 P0 的 APK 与真机环境）
         └ 老年用户试用实施与记录
第 3 周   P1-B 证据层核验 + P1-C 对比实验
第 4 周   P2-1 修 F6、P2-2 补单元测试；全文终审与导出
```

**关键路径说明**：老年用户试用（P1-A）**周期最长且需要外部人员配合**，必须**第 1 周就启动**；演示视频依赖稳定的 APK，放在 P0 之后。

## 六、两点必须避免的坑

1. **不要为了"看起来完整"把 P1/P2 的项目写成已完成。** 本报告目前最大的可信度来源，正是"明确区分已实现 / 部分实现 / 拟研发"——这个区分一旦破了，前面所有诚实披露都会贬值。
2. **不要用编造的老年用户数据。** 如果最终确实来不及做试用，就**保持现状写法**（"尚无正式试用数据，已列入计划"）——承认缺一项，比造假被查出代价小得多。
