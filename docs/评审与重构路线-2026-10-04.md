## 0. 先直接回答你的三个问题

**Q：这个项目是不是有很多问题？**
是，但问题分层很清楚，不能一概而论：

| 层 | 成色 | 说明 |
|---|---|---|
| 领域资产（中文证据语法、控件渲染、风险词表、坐标校准、平安看护、TTS 摘要） | **是真正的技术资产** | 这部分换任何 harness 都不会变简单，是论文与产品的贡献所在 |
| Android 平台落地 | **结构性欠债** | 无障碍树解析在主线程、每步全量落盘、麦克风无硬超时、大字号下 UI 被裁 |
| Agent harness 骨架 | **自造且欠债** | `AgentLoop` 1339 行 / 26 个可变字段 / 5 套互相干扰的停滞启发式 / 无上下文预算 |
| 声明与留档 | **对不上** | README 的数字多处与代码/留档不一致，核心指标 0 次有效观测 |

**Q：能不能借鉴 dsh？**
能，而且应该。但"借鉴"的准确含义是**抄它的 5 个骨架设计**（见 §4），不是抄代码，也不是把它装进 APK。

**Q：直接把 dsh 照搬到手机行不行？**
不行。有**两条互相独立**的理由，任何一条单独成立都足以否决：
1. **工程上跑不起来**（§2.1）：dsh 要 Node ≥22.19，且持久化、进程、图像、搜索都依赖原生模块（koffi/`node:zlib` zstd/sharp/node-pty/ripgrep）。
2. **就算跑起来，也搬不到你真正要的东西**（§2.2）：dsh **没有 GUI 观察-动作循环**，**也没有结果核验层**。你项目最难、最有价值的两块，恰好是 dsh 的空白。

> 反过来说，这是个好消息：你不需要"照搬"，你需要用 dsh 的骨架，把你自己那两块撑起来。

## 2. 为什么"照搬 dsh 到手机"不成立

### 2.1 工程上跑不起来

| 约束 | 实测事实 | 后果 |
|---|---|---|
| Node 版本 | `package.json`：`^22.19.0 \|\| >=24.0.0` | Android 上的嵌入方案（nodejs-mobile）长期停留在更低版本 |
| 原生模块 | `koffi` 出现在 fs-local、subprocess-local、**session-persistence-jsonl**、sandbox-windows-acl 等；`sharp` 在 attachment-local、spill-policy；`node-pty` 在 subprocess-local；`playwright` 在 inspector；`@vscode/ripgrep` 在 fs-search | 必须为每个 ABI 交叉编译，且**连会话持久化本身都依赖 koffi** |
| 压缩格式 | 会话文件用 `node:zlib` 的 zstd 帧 | 老版本 Node 无此 API |
| 社区维护状况 | nodejs-mobile 主线已被 fork 接续，并存在 [Android 16KB 页对齐问题](https://github.com/nodejs-mobile/nodejs-mobile/issues/148)；Termux 是 bionic，npm 的 linux-arm64 预编译产物通常无法 `require` | 你的目标机是 **Android 16 真机**，正好踩在这条线上 |

即使全部打通，还要再加上 Android 的 phantom process killer（会杀掉 dsh spawn 的子进程）、Android 14+ 前台服务类型限制、以及"让老人装 Termux"在产品上不可交付。**结论：路线 A（手机跑 dsh 本体）只能当内部实验台。**

### 2.2 就算能跑，也搬不到你要的东西

这一条更重要。逐项核对 dsh 的 `computer-use` / `browser-use` 包：

- `packages/computer-use/computer-use/src/` 只有 `brand.ts` + `index.ts` 共 63 行，服务只做 `register(name)`**预留一个提供方槽位**；真正的工具来自外部（Cua Driver MCP / Playwright MCP 等）。文档原文：「共享服务不包含通用桌面操作方法或模型控制的选择器」「**调用方负责协调完整观察、操作和验证流程**」。
- 也就是说：**"观察 → 动作 → 验证"这条循环在 dsh 里根本不存在**，它只提供挂载点。
- dsh 也**没有核验层**：循环直接信任 `tool/result`，`concludeTurn` 是工具自己声明"可以结束了"。全仓 grep `kind:'ask'` 的生产者只有 auto-review 与 Claude Code hooks 桥接——**连审批都不是默认路径**。

你的项目里最难的三件事——**在无障碍树上稳定定位并执行、判断"是不是真办成了"、分寸与交还本人**——dsh 一件都不提供。把 dsh 装进手机，你得到的是一套业务用不上的会话/插件骨架，以及一个新的崩溃面。

**它真正值得抄的是骨架纪律**，见 §4。

## 3. 问题清单

### 3.0 一句话诊断

> `core/` 是**披着 harness 外壳的手机领域状态机**。它的四个接口（`AgentPlanner`/`AgentTools`/`ActionApproval`/`AgentHook`）边界是干净的、值得保留；但 1339 行里约 1000 行是手机领域策略，而通用 harness 该有的东西（上下文预算与压缩、结构化工具注册表、tool-call 配对校验、事件流、检查点、权限模型）**几乎全缺**。真正的问题不是"agent 太难"，而是**没有单一真相源**：状态散落在 26 个可变字段和 5 套停滞启发式里；异常路径会破坏 transcript 不变量；最强的那道核验在手机上根本没接上。

### 3.1 P0（阻断级：安全承诺不成立 / 论文核心链路空转）

#### P0-A　手机上跑的生产路径**没有接入机械层与证据层核验**

- **证据**：`app/src/main/java/com/yinling/hotline/SessionController.kt:607`
  ```kotlin
  reviewer = CloudReviewer(config, log = { LoopLog.event(it) }),
  ```
  而机械层+证据层只在 `RuleReviewer` 里被调用：`core/src/main/kotlin/com/yinling/core/OutcomeCheck.kt:627-634`
  ```kotlin
  object RuleReviewer : CompletionReviewer {
      override suspend fun review(request: ReviewRequest): OutcomeVerdict = CompletionAudit.audit(...)
  }
  ```
  `CompletionAudit`（`OutcomeCheck.kt:576-588`）= `ClaimReader.read` → `OutcomeCheck.check`（机械：文字来源 / 时间锚点 / 动作影响）→ 只有通过才 `EvidenceCheck.check`。**这条链只被 harness 用**（`harness/Harness.kt:1675`）。
- **影响**：`README.md:30` 宣称的"三道严密逻辑铁门"、`docs/technical-review-2026-10-04.md` 里那批 X1/X4 对抗结论、harness 的核验矩阵——**全部是在 `RuleReviewer` 下测出来的，装到老人手机上的行为与它们无关**。这是本次评审最重要的一条：项目最强的安全论据目前是空转的。
- **修法（半天）**：让 `CloudReviewer` 内部**先**跑 `CompletionAudit.audit`，只有返回 `Supported` 才发起模型复核；或直接组合成 `MechanicalThenModelReviewer`。并把 harness 的 X1/X4 场景改成走**真机同款组合**。

#### P0-B　页面文字可以伪造"办好了"

- **证据**：`app/src/main/java/com/yinling/hotline/CloudPlanner.kt:424-435` 在 JSON 解析失败时对**整段原始输出**做正则兜底：
  ```kotlin
  val verdict = json?.optString("verdict")?.lowercase()?.takeIf { it.isNotBlank() }
      ?: VERDICT_TOKEN.find(raw)?.groupValues?.get(1)?.lowercase()
  ```
  `VERDICT_TOKEN = Regex("\"verdict\"\\s*:\\s*\"([a-z_]+)\"")`（`:460`）；而系统提示词又明确要求模型在 `citations` 里**原样引用页面文字**（`:476-483`，还特地叮嘱"把英文双引号换成「」"）。
- **影响**：一条含 `"verdict":"supported"` 的页面/短信/网页，就可能把 `unverified` 翻成 `supported`，然后手机**大声念出"办好了"**。对本产品的目标用户，这是最有害的一类错误。注意这正是 P0-A 的后果：本机机械层本来能拦住未执行动作的完成声明。
- **修法**：删掉正则兜底（JSON 解析失败一律 `Unverified`），或至少先剥离 `citations` 区域再匹配。代价是多问老人一句，收益是绝不假报成功。

#### P0-C　异常路径破坏 transcript 不变量，并**重放已经发生的动作**

- **证据**：`core/src/main/kotlin/com/yinling/core/AgentLoop.kt:896-1021` 的执行体只捕获 `CancellationException`（`:1010`）；`pending` 在 `:830` 置为整批，只在正常返回路径清空。`loop()` 的续跑分支是：
  ```kotlin
  // AgentLoop.kt:460-462
  if (pending.isNotEmpty()) { execute(transcript.lastIndex, pending)?.let { return it } }
  ```
  调用方把任何异常都当成"暂停"：`SessionController.kt:575-578`（`catch (error: Throwable) → phase = PAUSED`），且 `SessionController.kt:267-286` 会把这份损坏的 transcript 原样落盘。项目自己的 provider 契约明确禁止这种序列：`harness/mock_server.py:44-49`（`tool_call ... has no tool result` → HTTP 400）。
- **影响**：无障碍层抛错（服务断开、`SecurityException`、快照为 null 的 NPE）时，**整批动作会被再执行一遍**——手机上的点击/输入不可撤销。这与 `AgentLoop.kt:1010-1013` 注释承诺的 "never replay the actions that already happened" 直接矛盾（该保证只对取消成立）。另外被落盘的损坏 transcript 一旦 `restore()`，provider 直接 400。
- **修法**：每个 invocation 包 `try/catch (Exception)`，为失败项及其余项各补一条 `ToolResult(false, ..., "tool_error")`，`try/finally` 清 `pending`，返回 `PAUSED`；`restore()` 增加结构校验（每个 `assistant.toolCalls` 必须有配对 `TOOL`）。

#### P0-D　证据核验可被 agent 自己写入的文字"自证"

- **证据**：`AgentLoop.kt:669-693` 把**可编辑控件的当前文本**收进证据账本（`:672-674` 取 `element.text`/`description`），而 Android 侧对非密码输入框抓的正是节点文本（`app/.../ScreenAccessService.kt:265`，`if (node.isPassword) "" else node.text`）。也就是说 **agent 自己敲进任意搜索框的文字，下一轮就变成"页面观察到的证据"**。而 `EvidenceCheck.kt:70-83` 的审计**不读** `Observation.app/revision/step`，跨 app 事实可以互相担保。
- 第二条通道：声明里没有"效果词"时机械层直接放行——
  ```kotlin
  // core/src/main/kotlin/com/yinling/core/OutcomeCheck.kt:500
  if (!claim.assertsChange) return OutcomeVerdict.Supported
  // core/src/main/kotlin/com/yinling/core/EvidenceCheck.kt:69
  if (!claim.evidenceCheckable) return OutcomeVerdict.Supported
  ```
  `EFFECT_WORDS`（`OutcomeCheck.kt:339-359`）不含"读/看/查/帮"，所以"已经帮您看过了"这类声明 → 零动作、零证据 → `Supported` → 报 `COMPLETED` 并念给老人听。
- **影响**：论文核心论点"结果核验/证据链"在方法论上不成立——证据集合包含"我方写入的内容"，且**无法解析的声明默认判为已证实**而不是待核对。
- **修法**：(a) `Observation` 增加来源标记 `PAGE`/`AGENT_TYPED`/`TOOL`，审计只接受后两者；(b) 无效果词 + 含完成义（"了/好了/办完"）时默认 `Unverified`；(c) `EvidenceCheck` 用上 `app`/`revision`，跨 app 不互相担保；(d) 把"已经帮您看过了"补进回归用例。

#### P0-E　自动截图绕过审批，把屏幕图像直接发给云端视觉模型

- **证据**：`AgentLoop.kt:595-600` 的 `captureWhenBlind()` **自己调 `tools.execute`**，不走审批管线；审批只对"模型主动提出的调用"生效（`AgentLoop.kt:865-867`）。而工具目录明确声明截图需要同意（`core/.../PhoneTools.kt:173-176`，`needsApproval = true`），审批台词都写好了（`AgentLoop.kt:1278`）。blind 分支还缺 revision 去重（`graphicalShotRevision` 只覆盖 graphical 分支）。
- **影响**：在任意"文字在图像里/无控件树"的页面（课表、图表、WebView、小程序）上，屏幕截图会在**无人同意**的情况下持续上云。`needsApproval` 作为关键路径不变量被破坏——这与 P0-A 是同一个病根：**关键路径上的闸门没有变成结构保证，只是一处 if**。

#### P0-F　配对码可爆破 + 角色自选（服务端）

- **证据**：6 位、32 字母表（`server/app/db.py:122-125`，≈30 bit）、TTL 1 小时、**无失败计数/无限速/无锁定**（`db.py:152-158`）；`/join` 的角色由加入者自选（`server/app/main.py:212-224`，`role: str = Form(default="family")`，非法值也回落 `family`），加入页直接给 family 选项（`web.py:102-106`）。
- **影响**：拿到（或爆破出）配对码的人可自选"家人"，读全部上下文（`web.py:147-148`），并用 `POST /family/message` 让老人手机**用大字朗读"家人留言：…"**（`SessionController.kt:1011-1019`、`OverlayService.kt:564-601`）。这正是电信诈骗最需要的"熟悉的声音"通道。
- **修法**：`role=family` 必须由已配对设备/已存在家人确认；失败计数+指数退避+锁定（或 8 位一次性码）；新成员加入时给老人手机推一条不经模型的系统卡。

#### P0-G　会话明文长期落盘，而唯一交付物是 debug 包

- **证据**：`app/.../SessionStore.kt:48-62` 把每步完整 transcript（页面控件文字、输入内容、工具参数）明文写入 `filesDir/sessions/*.json`，无加密、无过期、无开关；`SessionController.kt:267-286` 每步调用。`app/build.gradle.kts` **没有任何 `buildTypes` 配置**，文档与 harness 全部使用 `:app:assembleDebug`。
- **影响**：`adb run-as com.yinling.hotline cat files/sessions/*.json` 即可拿到老人数月的办事记录（地址、取件码、聊天内容）；叠加 P0-F 等于隐私兜底全无。
- **修法**：加 `release` buildType 并规定装机只用 release；会话落盘前脱敏或加密（复用 `SessionStore` 的 Keystore 密钥）；至少"最近 N 条 + 7 天过期"；补 `dataExtractionRules`。

### 3.2 P1（高危：崩溃 / 卡死 / 误动作 / 误导老人）

| # | 问题 | 关键证据 | 后果 |

### 3.3 P2（整洁性 / 健壮性，都是具体缺陷）

- **计数器语义在 `resume()`/`answer()`/`restore()` 之间不一致**：`resume()` 只重置 `budgetStart`（`AgentLoop.kt:447`），保留 `repairs`/`cycleNotices`/`repeatCount`；`answer()`（`:362-374`）不刷新预算；`restore()`（`:402-410`）把 `step` 恢复成历史值而 `budgetStart=0`，第 39 步存档只剩 1 步。
- **26 个可变字段 + 22 行手工 `reset()`**（`:256-355` 声明、`:412-440` 重置）必须人工保持同步——新增字段忘写 reset 是必然的下一处 bug。
- **`cycleNotices` 会被一次非周期动作清零**（`:1064`），模型插入一个别的动作就能无限重置停机计数器。
- **重试策略粗糙**：`initialDelayMs shl failures` 无抖动（`:218-221`）；`generate()` 每次重试都念一遍"网络没有连上"（`:819`）；`failures` 是局部变量，跨步不累计。
- **证据/审计两侧看到的证据集不同**：`RuleReviewer` 看 60 条观察（`EvidenceCheck.kt:41`），模型 reviewer 的 `ReviewDigest` 只渲染最近 12 条×40 行（`OutcomeCheck.kt:644-671`）——所谓"规则基线 vs 模型核验"对照不是同一实验条件。
- **工具身份是字符串，散落 6 处**：`PhoneToolCatalog.specs`、`ManualActionPolicy.screenTools/tapTools`、`ScreenActionGuard.targeted/positional`、`AgentLoop.SCREEN_ACTIONS/REPEATABLE_TOOLS`、`OutcomeCheck.STATE_CHANGING`、6 个 `*_TOOL` 常量——且互相不一致（有的含 `tap`/`set_slider`，有的不含）。
- **批量执行是"每调用一次全树观察"**：`execute` 顺序执行（`:897`）且每次 dispatch 前 `tools.observe()`（`:977`），一个 3 调用批次 = 4~5 次全树快照。
- **app 层 0 个测试**：`SessionController` 直接依赖 `HotlineApp` 具体类，`AndroidPhoneTools` 依赖静态 `ScreenAccessService.active`，导致线程/生命周期这些最需要回归的地方无法在 JVM 上测。
- **`LoopLog` 无条件 `Log.d`，配对码与页面文字进 logcat**：`ServerClient.kt:186`（`code=$pairCode`）、`CloudPlanner.kt:57-61/154`（PAGE 全文）；服务端 `main.py:174` 记识别文本、`notify.py:32` 记家人手机号。
- **`lastScreenshot` 静态常驻**最后一张截图字节直到下次截图/进程结束（`ScreenAccessService.kt:78-81`）。
- **调试态与主循环并发操作无障碍层**：`censusOnce()`/`calibrateTap()` 与主循环同时 `snapshot()`/`dispatchGesture`（`SessionController.kt:304-324/331-455`），无互斥。
- **`OverlayService` 泄漏 + 可见性初值未应用**：`:156` 把捕获 `this` 的 lambda 挂到 Application 级回调，`onDestroy`（`:807-815`）不清空；`render()` 不调 `updateVisibility()`。
- **`ScreenAccessService.onServiceConnected` 无 try/catch 启动前台服务**（`:139-144`），Android 12+ 受限时会连带弄死无障碍服务；`BootReceiver` 同样裸调且 `exported="true"` 无 permission。
- **构建**：无 release/minify/签名；`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` 属商店敏感权限；`settings.gradle.kts` 把 aliyun 镜像排在 `google()`/`mavenCentral()` 之前且无 dependency verification。

## 4. 值得从 DSH 抄的 5 个设计（这是"借鉴"的正确含义）

每条都给出 Android/Kotlin 的落地形态。**只抄设计，不抄依赖**——不要让 koffi/sharp/Cordis/Electron/profile 进入你的技术选型。

### ① 仅追加事件日志 = 唯一真相源，"模型可见即已记录"
抄：`core/session/src/index.ts:860` 的 `deriveMessages()`；`docs/architecture.zh.md:131` 的不变量；`packages/core/agent-loop/src/agent.ts:671-686`（每轮从日志派生并深冻结）；`types.ts:432+` 的 `SurfaceOp.replace`。
**Kotlin 落地**：Room 单表 `session_event(seq PK, type, wall_time, turn, step, payload_json)` **只 INSERT** + `surface(seq, op, start_seq, end_seq)` 投影表；`deriveMessages()` 写成纯函数（可单测）；加一个 debug 不变量"重放请求 == 实际发送请求"。
**对你最大的额外收益**：这份日志天然就是"办成有证据"的证据链——何时看到什么页面、点了什么、系统回了什么，全部可审计、可给家人看、可直接作为核验输入。你现在的 `ledger` 是内存态、`restore()` 后清空（P1-11），正是因为缺这一层。

### ② 六段式工具流水线 + 单调 guard
抄：`docs/tool-execution-pipeline.zh.md:8-63`、`docs/subsystems/tools.zh.md:325-337,398-430`。
顺序：`tool/call` 落日志 → `pre-execute` 策略 → **单调 guard（只有 deny，没有 allow，顺序无法把拒绝翻回来）** → `execute` 包装 → 工具体 → `post-execute` → `result` 冻结落日志。
**Kotlin 落地**：`DeviceTool { spec; suspend fun execute(args, ctx): ToolOutcome }` + `ToolPipeline`（preHooks / guards / aroundHooks / body / postHooks / finalize）。
**关键**：把"老人安全红线"实现为**单调 guard**，而不是散落在 `execute()` 里的一串 if——这样 P0-E（自动截图绕过审批）在类型上就不可能发生。再补一个 dsh 没有的 `RiskLevel`（SAFE_READ / REVERSIBLE_WRITE / IRREVERSIBLE / SENSITIVE）。

### ③ 一次性授权升级阶梯（`escalate_to` + `justification`）
抄：`packages/sandbox/sandbox/src/escalation.ts` 全文 208 行——严格更宽表（`:28-31`）、理由必须成对且非空（`:51-61`）、schema 只广告闭合目标而"能否升级"按**执行时**该次调用的有效模式判断（`:22-41,174-179`）、只有 `allowed-once` 放行且**仅此一次**（`:188-207`）、拒绝文案教模型"停手解释，不要绕过"（`:203`）。
**Kotlin 落地**：把"文件效果"换成"手机动作"能力分级 `READ_SCREEN < NAVIGATE < INPUT_TEXT < SEND_MESSAGE < PAY`；工具 schema 暴露成对的 `escalate_to` + `justification`；审批 UI = 大字 + 一句人话理由 + "仅这一次"。这正好把 `README.md` 的"分级自主执行/交还本人"从口号变成机制。

### ④ turn/step 状态机 + 工具调用配对不变量
抄：`core/session/src/types.ts:201-229` 的七态 `TurnEndReason`（含 `interrupted`、`forked`）；`agent-loop/src/agent.ts:342-353`（失败步骤补写工具结果）；`tool-calls.ts:238-289`（**取消时为未启动调用补合成错误结果**、结果按模型顺序提交、用 `sourceEventSeqs:[callSeq]` 绑定）；`session-checkpoint-policy/README.md:98` 的 `TOOL_OUTCOME_UNKNOWN`。
**Kotlin 落地**：`sealed interface TurnEndReason`（所有 `when` 穷尽）+ `ToolCallLedger`，不变量"每个 callId 恰好一条 result"，每轮结束 debug 断言；**异常路径本身就是状态迁移，而不是逃逸**——这直接消灭 P0-C。
**对 GUI 自动化尤其重要**：「点了但不知道成没成」必须是**显式状态**，既非成功也非失败，文案指示"先核对页面状态或问老人"，**绝不自动重试**（点两次"确认支付"是灾难）。

### ⑤ 派生式上下文压缩
抄：`packages/compaction/compaction-basic/src/config.ts:20-23,75-79,191-198`（阈值 0.8、尾保留 0.16、headroom 65536）、`summarizer.ts:22-75`（八段固定模板、摘要包在 `<compacted-summary>`、**重放对话前缀以复用 provider KV cache**）、`docs/subsystems/compaction.zh.md:11-21`（`compaction/start` → summary + `surfaceOp:replace` → `compaction/end`，三种事件只写日志不进 surface）。
**Kotlin 落地**：先用启发式 token 估算；阈值抄 0.8、尾保留抄 0.16（按你云端模型的窗口换算）；摘要模板翻成中文八段并改写为老人场景（"Files and Code"→"涉及的应用与页面"，"Pending Jobs"→"还没办完的事"）；**强制保留**：老人原始诉求原话、已确认的关键信息（车次/地址/金额）、已完成动作与证据引用、待办下一步；替换节点前加中文 preamble（"这是自动生成的上下文检查点，当作既定背景，不要复述、不要提及压缩这件事"）。这是 P1-4 的正解。

**荣誉提名**：
- **能力 seam 三角色 + 单一提供方槽位**（`docs/glossary.zh.md:9`）——把 `UiDriver`/`ScreenCapture`/`AsrEngine`/`LlmClient` 定义成接口，注册第二个提供方直接失败。**这是让 app 层可测的前提**（现在 app 层 0 测试，就是因为 `AndroidPhoneTools` 硬依赖静态 `ScreenAccessService.active`）。
- **"续跑权限不持久化"**（goal round 上限 + 恢复后重新授权）——非常适合老人场景的安全默认值：智能体"自己接着干"的权限每次开机重新给。

1. 引入 **`session_event` 仅追加日志**（Room 或 JSONL+原子写），`deriveMessages()` 纯函数；`SessionStore` 改造成"日志提交 + 原子替换"（顺带修 P1-10）。

3. 把 26 个可变字段 + 手工 `reset()` 收成**显式状态对象**（`StallDetector`/`Budget` 值对象），并统一 `resume/answer/restore` 的预算语义（P2 前两条）。
4. 把 `Observation` 补上 `source`（PAGE/AGENT_TYPED/TOOL）与 `app`，证据审计开始使用 provenance（P0-D）。
5. **验收**：`AgentLoop` 净减 ≥200 行；新增不变量测试（重放请求==实发请求、每个 callId 恰好一条 result、异常路径不重放）。

### 阶段 2（1–2 周）：工具流水线 + 风险阶梯（抄 ②③）
1. `PhoneTool` 改成**单一 enum/sealed + 注册表**（消灭 6 处字符串清单）。
2. 六段流水线 + **单调 guard**；把 `ManualActionPolicy` 与 `ScreenAccessService` 里的敏感判断合并成**唯一一处 guard**（消灭双词表）。
3. 引入 `RiskLevel` 与 `escalate_to`+`justification` 一次性授权；审批下沉到流水线（消灭 P0-E）。
4. `validate()` 做类型与区间校验，删掉执行侧的魔法默认值（P1-7）。
5. `app` 层抽出接口（`UiDriver`/`ScreenCapture`），**先在 JVM 上给 `SessionController` 补并发序列测试**。

### 阶段 3（1–2 周）：上下文与性能（抄 ⑤）
1. token 预算 + 派生式压缩（0.8/0.16 + 中文八段 checkpoint）。
2. 流式 LLM 客户端（OkHttp SSE）+ 按 `code` 分类的文案（P1-15）；**顺带修掉 `HttpURLConnection` 阻塞读无法被取消**的问题——现在"停下来"按钮按下去也中止不了在途请求。
3. 无障碍树解析移出主线程；静态设备事实（`launchableApps`/屏幕尺寸）从 `ScreenSnapshot` 拆出（P1-4/P1-9）。
4. 麦克风硬超时 + 打断二次确认（P1-12/P1-14）；适老 UI 大字号验收（P1-16）。

### 阶段 4：技能闭环与评测

## 6. 保留 vs 重写

**保留（这是你的技术资产）**：四个接口边界；`PhoneToolCatalog.render`（控件编号/键盘候选/滑块档位/无名叶子带坐标）；`ScreenActionGuard.rebind`（几何+去几何双通道身份，测试扎实）；`Lexicon`（中文数字/单位/字段折叠）；`PeaceWatch`；`SpokenSummary`/`MarkdownLite`；`AgentOutcome` 的 7 种收尾语义。

**重写（抄 dsh 骨架）**：`AgentLoop` 的 26 个可变字段与停滞启发式；会话持久化；`ManualActionPolicy` 的关键词判定（改成 guard + 风险分级）；`CloudPlanner` 的 provider 协议手写（抽成 LLM 客户端 seam）。

**别动但要改口径**：`harness/Harness.kt`（作为评测资产保留，但 `findings` 必须能导致非零退出；`renderScreen` 默认值是 `{ "" }` 导致 67/70 个单测实际上没把页面交给模型，建议改成必填或默认 `PhoneToolCatalog.render`）。

## 7. 比赛前最容易被问倒的 5 条与改法

1. **「系统说办成、实际没办成必须为 0」** → 改成"已定义该指标与采集口径（人工真值 + 4 类机器真值，`run.py:60`）；当前留档 25 次运行中真值样本 0 条，因此本次不报告该数值"，并原样附上 25 行。
2. **「13 类任务实测步数/耗时」表** → 每行标注运行编号/日志文件/模型/确认模式；无留档的行注明"历史记录，原始日志未入库"。
3. **计数口径** → 改成"harness 31 组场景、180 条断言（本次实跑）；pytest 32 项；core 单测 70 项"，并把并存的 47/70/73/74/149/155 六个数统一。
4. **「三道铁门 / 100% 拦截物理不可能」** → 改成"机械一致性核验覆盖文字来源、时间锚点、改变类动作三类**必要条件**；`Supported` 仅表示必要条件通过"，并明写 F5 六项隐蔽动作仍漏拦是词表路线的已知上限。
5. **「付款/发送/删除绝对不碰」** → 说明留档运行中危险动作是**自动确认模式下的词表**挡下的（14 行 `auto_confirm=true`），生产确认模式下的打扰次数与人工闸门尚无有效样本。

补充（README 未写、最易被追问）：手机→服务端全明文 HTTP（`README.md:166` 就是 HTTP 部署）；`/api/device/pair` 匿名可调导致讯飞额度可被白嫖；配对码无失败限速且会进访问日志。

## 8. 建议的下一步

按"性价比"排序，前三条建议这周就做：

1. **阶段 0.1**（半天）：把 `CompletionAudit` 接回真机路径。这一步几乎零风险，却能把项目最核心的安全主张从"空转"变成"真的在跑"。
2. **阶段 0.3**（半天）：修异常路径的动作重放。这是唯一一条会造成**不可撤销的物理后果**的缺陷。
3. **阶段 0.5/0.6 + §7**（1 天）：README 口径统一 + 打 release 包。成本最低、对答辩收益最大。
4. 然后按阶段 1→3 推进。**不要做的事**：不要在 Android 里塞 Node/dsh；不要指望 dsh 提供 GUI 循环或核验层；不要让 `koffi`/`sharp`/Cordis/Electron 进入技术选型。

> 最后回应你最初的感受："agent 太难了"——难的不是 agent，是**你同时在写三样东西**：一个 agent harness、一个无障碍自动化引擎、一个适老安全产品。dsh 能帮你省掉第一样里"骨架该有的纪律"，但省不掉后两样——而后两样恰恰是别人做不出来的部分。把骨架换成有纪律的，把精力留给证据核验和分寸感，这个项目就成立了。
